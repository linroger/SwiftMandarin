## Part B — Audit: Bugs, Bottlenecks & Issues

### Executive summary

SwiftMandarin is a feature-rich, ambitious SwiftUI Mandarin-learning app whose breadth (8 tabs, 10-provider AI abstraction, on-device + cloud translation, photo OCR, screenshot stitching, workbook grading, spaced repetition, bilingual UI) outpaces the robustness of its foundations. The codebase is functional but carries three structural risks that should be treated as release-blockers. (1) PERSISTENCE FRAGILITY: every persisted model uses synthesized Codable with no CodingKeys, no schemaVersion, and no defaulting (confirmed by grep across Models/). The PersistentCodableStore .backup is the SAME schema, so any future non-optional field throws keyNotFound on BOTH decode paths and silently wipes all user vocabulary/progress/history on update. Collection decode is all-or-nothing, so one corrupt row drops the whole array. This is the single highest-leverage area to harden. (2) CORRECTNESS BUGS IN CORE FLOWS: the History store records the UI-toggle direction instead of the actually-translated direction (confirmed TranslateView.swift:889 vs :959/:975), corrupting every cross-direction entry and everything derived from it; the audio pipeline spawns a non-Sendable AVAudioPCMBuffer into a per-buffer Task (use-after-free + reordering), and the sample-rate converter re-feeds the same buffer forever; screenshot stitching mixes a padded source stride with an unpadded render buffer, corrupting overlap detection; CSV round-trip is lossy for any multi-line field. (3) IA/DISCOVERABILITY DEBT: on the now-live iOS 17 path the legacy TabView emits 8 tabs with no compact-width gating (confirmed ContentView.swift:148-179), so tabs 5-8 — including the app's OWN More tab — collapse under the system More overflow, a confusing collision. The genuinely valuable workbook-grading feature is reachable through exactly one buried sheet (PhotoTranslateView.swift:210) and nothing else. The More tab is a 601-line catch-all with a duplicate divergent History screen, dead settings, a placeholder App Store ID, and a privacy link pointing at apple.com. Strategically, the app is one solid refactor of the data layer, the information architecture, and a unified translation/learning-direction model away from being genuinely excellent. Concurrency safety is also unverified by the compiler (SWIFT_STRICT_CONCURRENCY is unset), masking the audio races. Recommend: freeze new features, ship the persistence envelope + the history-direction fix + the audio-buffer fix first, then execute the IA consolidation (5 tabs + real More hub) and a single source-of-truth learning-direction model.

### Top prioritized issues

**B1. [CRITICAL] Schema evolution will silently wipe all user data on the next model change**  
- *Why:* All persisted models (SavedTerm, CardProgress, DailyActivity, history) use synthesized Codable with no schemaVersion/CodingKeys/decode defaults (verified: grep finds none in Models/). PersistentCodableStore.load decodes the whole collection at once and the .backup is the same schema, so adding any non-optional stored property throws keyNotFound on BOTH the primary and backup decode, and load() returns nil — every saved word, flashcard, streak, and history entry is dropped on update. One corrupt element also discards the entire array.  
- *Fix:* Introduce a versioned envelope {schemaVersion:Int, data:T} in save/load. Decode tolerantly: give new fields explicit decodeIfPresent defaults via custom init(from:), and add a per-element resilient decoder (decode [FailableDecodable<Element>], keep successes, log/drop only the truly-corrupt rows). Ship this BEFORE any further model changes so existing 0.x payloads survive the upgrade.

**B2. [HIGH] History records the UI-toggle direction, not the translated direction — corrupts every cross-direction entry**  
- *Why:* Confirmed: triggerTranslation computes actualDirection = detectedTranslationDirection from input content (TranslateView.swift:889), but performTranslation (line 959) and triggerAITranslation (line 923) snapshot directionSnapshot = sharedState.direction (the UI toggle) and write THAT into handleCompletedTranslation (line 975). When the toggle says EN→中 but the user types Chinese, the engine correctly returns English yet history stores direction=englishToChinese. TranslationHistoryEntry.chineseText/.englishText key off direction, so source and target are mislabeled through History, restore, and any term saved from a restored entry.  
- *Fix:* Thread the detected direction through: compute actualDirection = detectedTranslationDirection in performTranslation/triggerAITranslation and pass that (not sharedState.direction) to both the guard comparison and handleCompletedTranslation's direction: argument. Keep the source-text snapshot guard.

**B3. [HIGH] Audio tap captures a non-Sendable AVAudioPCMBuffer into a per-buffer Task (use-after-free + reordered/garbled audio)**  
- *Why:* SpeechRecognitionService.swift:440-446 spawns Task { await self.processAudioBuffer(buffer) } per tap callback. AVAudioEngine reclaims that buffer once the closure returns, so the async read touches recycled memory; tens of unstructured Tasks/sec hop to the MainActor with no FIFO guarantee (frames reorder), and in-flight Tasks outlive stop()/removeTap, yielding into a finished continuation. Separately the sample-rate converter input block (lines 473-476) always returns the same buffer with .haveData, so the converter can loop/duplicate frames and never signals end-of-stream.  
- *Fix:* Do conversion synchronously inside the tap and call inputContinuation?.yield(...) directly (the continuation is Sendable/thread-safe); never spawn a Task per buffer. If a hop is unavoidable, deep-copy the buffer first. In the converter block return .haveData once per input chunk then .noDataNow, and size output with ceil(ratio*frames).

**B4. [HIGH] iOS 17 phones collapse tabs 5–8 under a system More that collides with the app's own More tab**  
- *Why:* Confirmed ContentView.swift:148-179: legacyTabView emits 8 Tabs with no compact-width gating. On iPhone the classic UIKit TabView shows 5 items and pushes the rest (learn, phrases, stats, AND the app's .more) into the OS More list. Deployment target was just lowered to iOS 17 (commit 82130c4), so this is live for all iOS 17 users — a confusing double-More.  
- *Fix:* Cap iPhone to ≤5 primary tabs (Translate, Photo, Vocabulary, Learn, More) and fold History (already duplicated in More), Phrases, and Stats into More or their parent screens. Drive both compact and regular layouts from one AppTab source.

**B5. [MEDIUM] Screenshot stitching reads pixels with the wrong bytesPerRow, corrupting overlap detection**  
- *Why:* getPixelData renders into a context whose stride is 4*width (no padding) but findOverlapHeight indexes that buffer using the ORIGINAL CGImage's bytesPerRow (often padded to 16/32/64-byte alignment). Every row offset is wrong; the bounds guard then silently skips most comparisons, so overlap detection is effectively broken and stitched screenshots mis-join.  
- *Fix:* Return and use the same stride the buffer was allocated with (4*width) inside findOverlapHeight; never mix the source CGImage's bytesPerRow with a freshly-rendered 4*width buffer. Only scan the overlap strip rather than allocating full-image buffers for both images.

**B6. [MEDIUM] Vision OCR runs synchronously on the MainActor and silently drops images on non-vision providers**  
- *Why:* PhotoTextRecognitionService is @MainActor and calls handler.perform([request]) synchronously, so accurate-level OCR on a tall stitched screenshot blocks the main thread for seconds. Separately, cleanupRecognizedText/extractVocabulary pass imageData without checking provider.supportsVision; deepseek/minimax fall back to the text model and CloudAIService strips the image entirely, so vision tasks silently run text-only.  
- *Fix:* Make the Vision perform nonisolated/off-actor and hop back to MainActor only to publish results. Gate image paths on provider.supportsVision (reuse gradingProvider()); only pass imageData to chat() when the resolved provider actually supports vision.

**B7. [MEDIUM] CSV import corrupts any entry whose quoted field contains a newline**  
- *Why:* parseCSVImport pre-splits the whole file on newlines, but export quotes embedded newlines into a single multi-physical-line field. On re-import the splitter shreds that record, parseCSVLine sees unbalanced quotes, and the row is dropped or mangled — backup/restore is lossy for any multi-line definition.  
- *Fix:* Replace with an RFC 4180 state-machine parser that tracks quote state across physical line boundaries (accumulate until quotes balance). Add a golden round-trip test: export a term whose definition contains a newline/comma/quote, re-import, assert equality.

**B8. [MEDIUM] Spaced-repetition scheduling is structurally wrong and the correct code is dead**  
- *Why:* getCardsForReview/getDueCards (due-ordering + 20-card cap) have ZERO call sites; sessions are built by filteredStudyCards in raw deck order with no cap, so a 500-word deck becomes one 500-card session and 'Due for Review' shows due cards unordered. recordReview re-derives previousInterval from dates (collapses to ~1 day after a lapse, so intervals never grow), and quality 2 ('Difficult') is silently counted as INCORRECT. LearningCard.id is the Chinese string, so built-in and vocabulary cards collide in the progress dictionary and English-direction cards with empty Chinese all map to id=='', sharing one bucket.  
- *Fix:* Route reloadSessionCards through getCardsForReview(from:limit:). Persist a real interval/lapses on CardProgress (SM-2 style) instead of re-deriving from dates. Give cards a stable namespaced id ('builtin:<chinese>' / 'vocab:<SavedTerm.id>'). Decide explicitly whether 'Difficult' passes or lapses and make the thresholds agree.

**B9. [MEDIUM] Workbook grading and other power features are nearly undiscoverable**  
- *Why:* Confirmed: WorkbookGradingView is presented from exactly one place (PhotoTranslateView.swift:210) and has no top-level tab, no More entry, and no Shortcuts route. Camera scanner and screenshot translation are reachable only via App Intents; vocabulary import/export is macOS-only. A paid-vision-call feature that users will want to revisit is hidden, and grading results are lost on dismiss (no persistence).  
- *Fix:* Add a discoverable entry (primary/overflow action on Photo, plus a More hub row), persist gradings in a GradingHistoryStore (timestamp, score, questions, thumbnail) with a history list, and surface import/export on iOS. Add an onboarding tip pointing to Learn/Workbook.

**B10. [MEDIUM] Strict concurrency checking is off, so the audio data races compile clean**  
- *Why:* SWIFT_STRICT_CONCURRENCY is unset (Swift 5 mode) and Speech/AVFoundation are @preconcurrency-imported, so the genuinely off-actor buffer/converter/completion-handler races are never checked by the compiler — exactly the code where the use-after-free lives.  
- *Fix:* Set SWIFT_STRICT_CONCURRENCY = complete on Debug, triage the warnings (they land on the audio tap/converter/continuation paths), then move toward Swift 6 mode. This converts the latent races into compile-time errors.

- **Audio tap retains AVAudioPCMBuffer across async hop without copying — data race on reused buffer memory** (speech): The claim does not hold up. The cited code (SpeechRecognitionService.swift:440-446 and :458-485) does capture the tap-delivered `buffer` into an escaping `Task` that reads it asynchronously on the MainActor. However, the claim's foundational premise — that "AVAudioEngine ... its backing storage may be reused for subsequent taps" so reading it later is a data race / undefined behavior — is incorrect for AVAudioPCMBuffer.  Mechanism (independent analysis): 1. AVAudioPCMBuffer is a reference-counted Obj-C (NSObject) class that OWNS its sample storage via its AudioBufferList. Capturing it in the `Task { await self.processAudioBuffer(buffer) }` closure causes ARC to retain the buffer object; both the object and its owned `mData` audio memory stay alive and unmodified as long as that strong reference exists. AVAudioEngine allocates a fresh AVAudioPCMBuffer for each tap callback — it does not overwrite the mData of a buffer you have retained. So at line 467 (`buffer.frameLength`/`buffer.format.sampleRate`), in the converter pull-block at 473-476 (returning `buffer`), and at line 483 (`AnalyzerInput(buffer: bufferToSend)`), the buffer's samples are not subject to concurrent overwrite. There is no reused memory and therefore no data race on it. 2. Apple's own AVAudioNodeTapBlock documentation describes the block as receiving "copies of the output of an audio node" and carries NO "valid only for the duration of the block / must copy if retained" warning — unlike the explicit pool-reuse warnings Apple places on CMSampleBuffer from AVCaptureVideoDataOutput. The claim attributes CMSampleBuffer-style pool-recycle semantics to AVAudioEngine taps, which is not how this API behaves. 3. Retaining a tap buffer and processing it later via an async hand-off (continuation.yield / Task) is the conventional, Apple-sample-endorsed pattern for feeding SpeechAnalyzer; it would be broken if the buffer were unsafe to retain.  Note: there are unrelated latent concerns in this code (spawning an unordered Task per tap on the MainActor could reorder/drop audio chunks under load; the AVAudioConverter single-buffer pull-block is fragile), but none of those is the claimed defect. The specific claim — a data race / UB from reading reused/overwritten buffer backing storage — is not real and not reachable, because AVAudioPCMBuffer is reference-counted and the retained reference keeps the memory alive and stable. Verdict: invalid.
- **processAudioBuffer mutates AVAudioConverter from concurrent Tasks with no serialization** (concurrency): The claim's core mechanism is false. ModernSpeechEngine is @MainActor-isolated (SpeechRecognitionService.swift:360), and processAudioBuffer (lines 458-485) inherits that isolation, so all invocations serialize on the MainActor — there IS serialization, contradicting the claim's "no serialization" headline and "race" category (the claim even concedes "calls serialize on the actor"). Critically, processAudioBuffer contains NO await/suspension point: reading audioConverter (464), allocating convertedBuffer (465-468), and the synchronous converter.convert(...) call (473-476) all run as one atomic, non-suspending MainActor block before inputContinuation.yield (484). Because the actor serializes invocations and there is no interior suspension point, no second invocation can interleave with an in-flight conversion. The `buffer` captured by the inputBlock at line 475 is the per-call parameter of the currently-executing invocation (a local binding), not a shared field — so it can never return another task's "wrong/stale buffer." The alleged "concurrent use of AVAudioConverter" / "wrong buffer handed to converter" / "interleaved buffers" scenario is therefore impossible and unreachable. The only genuine residual concern is unrelated and much narrower: each tap spawns an unstructured Task { await self.processAudioBuffer(buffer) } (lines 443-445), and unstructured tasks have no guaranteed scheduling order, so 4096-frame buffers could occasionally be fed to the converter slightly out of capture order. That is a different defect from the one claimed, and its impact is low (minimal/inaudible resampling effects from rare reordering, no data corruption, no concurrent converter access). Defaulting to not-confirmed because the described defect does not hold up; adjusted severity to low to reflect the minor real residual ordering nuance.
- **WordTranslationService cache is mutated off the main actor without synchronization (data race)** (components): The claim's textual evidence is accurate (WordTranslationService at /Users/rogerlin/XCode-Projects/SwiftMandarinShortcuts/SwiftMandarin/Services/WordTranslationService.swift:14-22 is an @Observable final class, not source-annotated @MainActor, no Sendable, no lock; translationCache is read/written across await boundaries at lines 33-39, 49-55, 84-137; called from .task in RubyTextView.swift:438/444 and EnglishRubyTextView.swift:293). But the load-bearing premise — that this code runs off the main actor on a cooperative thread pool — is false for this project.  The Xcode project sets SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor for BOTH Debug and Release of the app target (project.pbxproj lines 352 and 425, under the target buildSettings with PRODUCT_NAME = $(TARGET_NAME)), together with SWIFT_APPROACHABLE_CONCURRENCY = YES. Under default-isolation=MainActor, every declaration lacking explicit isolation is implicitly @MainActor. I grepped all three cited files and found NO nonisolated, @concurrent, actor, Sendable, or explicit @MainActor annotations. Consequently WordTranslationService, its translationCache property, and all its async methods are implicitly @MainActor-isolated, as are fetchWordDetails(), translateWord(), and the enclosing .task closures.  An @MainActor async method runs on the main actor; it only suspends (off the actor) at the await on the underlying TranslationSession/AI call, then resumes on the main actor before writing translationCache. All cache reads/writes are therefore serialized on the single main actor. Two concurrent popovers or batch translation all execute on the main actor — there is no concurrent dictionary mutation, no data race, and no path to EXC_BAD_ACCESS from this code. The proposed fix (add @MainActor / convert to actor) is redundant because MainActor isolation is already applied module-wide via the build setting. The defect as described (an unsynchronized off-main-actor data race) is not reachable; marking invalid.

## Part C — Architecture & Workflow Recommendations

> These make the app more powerful, robust, intuitive, and streamlined. They are **documented, not yet implemented** — out of scope for this session's feature work, recommended as the next roadmap (the data-layer + history-direction + audio-buffer fixes are release-blockers).

### Architecture

**C1. Versioned, resilient persistence layer with batch APIs and off-main encoding**  
- Wrap every store payload in {schemaVersion:Int, data:T}; on load switch on version to run incremental migrators and decode new fields with decodeIfPresent defaults. Add loadCollection that decodes [FailableDecodable<Element>] so one bad row never drops the array. Add addMany/replaceAll and a withBatch{} that suspends the didSet save() until completion (kills the O(n²) save amplification on import). Make save() nonisolated/debounced so large JSON encodes leave the MainActor, and consider moving the larger collections (vocabulary, history, progress) to a JSON file in Application Support instead of UserDefaults.  
- *Benefit:* Eliminates the single biggest risk (silent data loss on update), bounds corruption to truly-bad rows, removes main-thread hitches and import jank, and gives a clean path for every future model change.

**C2. Collapse to a 5-tab frequency-ordered IA with one real More hub**

Fold History into a single canonical screen in More (delete the duplicate HistoryView/HistoryRow in MoreView.swift:66-163 and route to HistoryTabView), reach Stats from inside Learn/More (remove the duplicate Stats tab and the in-Learn LearningStatsSheet), and move Phrases under a Library grouping. Give StatsView its own NavigationStack for consistent nav chrome. Drive compact and regular layouts from one AppTab source.

- *Benefit:* Directly fixes the history-direction corruption bug and the inert .bilingual mode, eliminates the App-Language/Learner-Mode divergence, and removes a whole class of direction bugs by construction.

Route TranslateView, LiveSpeechTranslationView, WordTranslationService, ScreenshotTranslationStore, and the Intents through it; add in-flight de-duplication keyed by cacheKey.  
- *Benefit:* Removes duplicated, already-drifting availability gates (some at 18, some at 26), makes the unofficial-API risk fixable in one place, gives clean cancellation, and lets iOS 18–25 use fast batch translation instead of the serial AI fallback.

**C6. Unify settings into one declarative cross-platform definition and prune dead controls**

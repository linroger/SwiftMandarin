### 2026-07-21T14:27:39Z — `codex/async-audio-session`

- Bug: iOS 27 Thread Performance Checker reports synchronous `AVAudioSession.setActive` calls from the `@MainActor` speech router, risking UI hangs during local and MiniMax playback activation/deactivation.
- Baseline: clean isolated worktree at current `origin/main` commit `bd8acb1`; the unrelated dirty primary checkout remains protected.
- Root cause: `SpeechService.configureAudioSessionForPlayback()` and `deactivateAudioSessionIfIdle()` synchronously mutate session activation on the main actor. The Xcode 27 SDK provides async `activate(options:)` and `deactivate(options:)`, both returning `Bool`; the iOS 17 deployment target requires a non-main compatibility path.
- Concurrency risk: a direct fire-and-forget conversion can let stale speech deactivation land after recording or source-audio playback takes ownership. Pending playback activation must also remain request-scoped so a stopped/replaced request cannot begin late.
- Tests pending: deterministic activation ordering, cancellation/replacement, idle deactivation, source handoff, source integration guard, and fresh macOS/iPhone/iPadOS 27 builds.
- Next steps: implement one ordered audio-session transition boundary, route speech playback through an awaited request-owned activation gate, then complete regression and platform gates.

Without it, tidying up a word mastered last month would silently erase a milestone earned this morning; with it, a mis-tap nets to zero on the same day and an old word debits its own day. Terms mastered before this shipped carry `nil` and were never counted, so their undo is correctly a no-op.

A refund never takes a day below zero and never creates a record for a day that has none.

### 2026-08-10 — macOS cards were drawn in the page color

- Report (with a screenshot of Home in Dark appearance): "the background and the the rounded rectangle background are the same color. fix this on macos".
- Confirmed by sampling the screenshot: page and every card interior were both `rgb(30,30,30)`, a delta of exactly 0. Not "nearly identical" — identical.
- Root cause: `SMTheme.pageBackground` used `NSColor.windowBackgroundColor` and `SMTheme.cardFill` used `NSColor.controlBackgroundColor`. That reads like the canonical page/card pairing, but AppKit resolves BOTH to the same value — measured `#FFFFFF` in Aqua and `#1E1E1E` in Dark Aqua. Every card in the app was therefore filled with exactly the page color, in both appearances, leaving only a 0.75pt hairline (and a 6%-black shadow, invisible on a near-black page) to suggest a card existed. The file's own comment said the two were "nearly identical", so the problem was known in outline and under-corrected rather than unnoticed.
- Fix: each surface now picks a *different* system color per appearance, always arranged so the card is the lighter one. Dark → page `windowBackgroundColor` (so the page still meets the toolbar and window frame seamlessly) and card `underPageBackgroundColor`. Light → page `underPageBackgroundColor` and card `controlBackgroundColor`, which is the same direction iOS gets from its grouped colors. Measured result: light 246 → 255 (+9), dark 30 → 40 (+10). The stroke went to full separator strength and the shadow is appearance-aware (6% black in light, 45% in dark, where a 6% shadow is invisible).
- The dark test is `bestMatch(from: [.aqua, .darkAqua]) == .darkAqua`, not `name == .darkAqua`: the latter classifies the high-contrast dark appearance as light and would hand it a white card on a black page.
- Also folded `StatsView` into the shared surfaces. It was bypassing the design system entirely — `Color(.windowBackgroundColor)` for the page and `.background(.background, in: RoundedRectangle(...))` for all five panels, the latter being a SwiftUI ShapeStyle that also resolves to the window background, so those cards had no border either. Now `SMTheme.pageBackground` + `.smCardSurface()`.
- Files: added `scripts/macos-surface-checks/MacOSSurfaceChecksRunner.swift`, `scripts/test-macos-surfaces.sh`; updated `Views/Components/DesignSystem.swift`, `Views/StatsView.swift`, `init.sh`, `feature_list.json`.
- Tests: `zsh init.sh` green including the new 8/8 surface checks and 6/6 wiring checks. The runner resolves the live system colors in all four appearances (Aqua, Dark Aqua, and both high-contrast variants) and fails if the pair a surface uses is closer than 6/255 or if the card is the darker one — so a future macOS that collapses another pair fails loudly instead of silently flattening the UI. It also asserts the original trap still exists, so if Apple ever separates `windowBackgroundColor` from `controlBackgroundColor` the check tells us to simplify rather than silently keeping a workaround. Mutation test: restoring the old pairing fails with "page #FFFFFF and card #FFFFFF differ by 0.0/255".
- Self-review caught a defect in the check itself before it shipped: the failure message read the captured `NSColor`s *after* leaving the appearance block, and since they are dynamic colors they re-resolved against the machine's current appearance — the first mutation run printed "NSAppearanceNameAqua: page #1E1E1E", mixing an Aqua label with Dark Aqua values. Descriptions are now rendered inside the block.
- Verified in the running macOS app on both appearances, with before/after pixel sampling: Home went from delta 0 to delta +10, and Statistics — which had been completely flat — now shows every panel. Light appearance was checked by toggling the system setting and restored afterwards.
- Not done: not verified on a physical iOS device. The iOS branches of `SMTheme` are untouched; `StatsView` does change on iOS, from the `systemBackground`-backed ShapeStyle to the same `secondarySystemGroupedBackground` card surface the other eleven screens already use, which is a consistency fix rather than a new pattern.
